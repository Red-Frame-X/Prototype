## 1. ネットワークルール［通信ブロック］

通信そのものを根元から遮断します。DNR上限を圧迫しないよう、正規表現の乱用を避け、可能な限りプレーンなホスト名指定を行うのが基本です。ルールの末尾に `$` を付け、カンマ `,` 区切りで修飾子（Modifiers：フィルタが適用される条件や通信の制御方法を指定するためのパラメータ記法）を指定します。

### 1.0 URLパターンの基本記号

* `*`：0文字以上の任意の文字列に一致するワイルドカードです。
* `||`：指定したドメインとそのサブドメインに一致します。例：`||example.com^`
* `^`：英数字および `_`、`-`、`.`、`%` 以外の区切り文字、またはURL末尾に一致します。`||example.com^` が `example.com.evil.test` を巻き込むことを防ぎます。
* `|`：パターンの先頭ではURL先頭、末尾ではURL末尾を固定します。例：`|https://example.com/|`
* `@@`：一致するブロックルールを解除する例外マーカーです。例外の範囲は修飾子で必要最小限に絞ります。

`|`、`||`、`^` はURLパターンを持つネットワークルール用の記号です。コスメティックルールのドメイン指定には使用しません。正規表現ルールは柔軟ですが、通常のURLパターンより評価コストと保守負担が大きいため、単純なパターンで表現できない場合に限定します。

### 1.1 基本的な適用と除外
### `$document` ［ページドキュメント全体の適用・除外］
* **構文例**： `||example.com^$document` ［ブロック］ / `@@||example.com^$document` ［例外］
* **概要**： ブラウザが最初に読み込むメインHTML［ドキュメント］そのものに対するリクエストにマッチします。
* **解説**： サイトが根本的に破損した場合のデバッグや、信頼できる特定サイトのみを全解除（ホワイトリスト化）する際に多用できる非常に強力な機能です。一方で、その強力さゆえに誤用すると広告を素通ししてしまうリスクを伴います。AdGuardではシステムレベルでの介入となるため、実機での慎重な検証が求められます。

### `$subdocument` ［サブドキュメントの適用・除外］
* **構文例**： `||example.com/ad-frame.html^$subdocument` ［ブロック］ / `@@||example.com/ad-frame.html^$subdocument` ［例外］
* **概要**： メインドキュメント内に埋め込まれた `<iframe>` や `<frame>` 要素を介して読み込まれる通信にマッチします。
* **解説**： 広告用フレームやSNSウィジェットを外枠ごと遮断でき、個別のスクリプトを追う必要がないためルール数を節約できます。ただし、決済フォームやログイン用外部フレームなどを巻き込んでサイトを破損させる誤爆（False Positive：本来ブロックすべきではないサイトの正規リソースや機能を、誤って広告やトラッキングと判定して遮断し、サイトの表示や動作を破損させてしまう現象）リスクには注意が必要です。

### `@@` ［例外ルール / ホワイトリスト］
* **構文例**： `@@||example.com/ads.js$script`
* **概要**： 先頭に付与することで、指定した条件に合致する通信や要素のブロックを解除します。
* **解説**： GitHub等でのFalse PositiveのIssues（イシュー：GitHub等のバージョン管理プラットフォームにおいて、ソフトウェアのバグ報告、機能リクエスト、フィルタの誤爆対応や改修要件を追跡・管理するためのタスクおよび議論のスレッド）報告時に、「このルールを追加すれば直る」という回避策（Workaround：根本的なフィルタやスクリプトの不具合修正が完了するまでの間、一時的に問題やサイト破損を回避するための応急的な処置や解決策）を即座に提示する用途で活躍します。ただし、条件を緩くしすぎるとブロックすべき悪質なトラッカーまで通過させてしまうため、リソースタイプ修飾子と併用して影響範囲を絞り込むことが必須となります。

### 1.2 対象と適用範囲の限定
### `$app` ［アプリ単位の適用限定］※ OSレベルアプリ特化
* **構文例**： `||ads.example.com^$app=com.twitter.android`
* **概要**： システム全体を監視するAdGuard環境において、特定のアプリにのみルールを適用します。
* **解説**： 他のアプリの正常なバックグラウンド通信を一切妨げずに特定アプリの広告のみを制御できる反面、デスクトップ版のブラウザ拡張機能では完全に無視されるため、クロスプラットフォームでのルール共有には不向きです。

### `$domain=` / `$denyallow=` ［適用先の限定と除外］
* **構文例**： `||example.com/ads.js$domain=test.com|~sub.test.com`
* **構文例**： `||example.com^$denyallow=sub.example.com` ［サブドメインの除外］ / `*$denyallow=com|net` ［特定のTLD〈Top-Level Domain / トップレベルドメイン：「.com」「.net」「.jp」など、ドメイン名において一番右側に位置する最上位の階層名〉の除外］
* **概要**： `$domain` は指定ドメインでのみ有効にし、`~` で特定サブドメインを除外します。`$denyallow` は「指定ドメイン以外」のすべてで適用します。
* **解説**： 複雑なサイト群におけるFalse Positiveを極めて正確かつ柔軟にコントロールできます。一方で、サイト運営側でサブドメインの運用が変更された際、ルールのメンテナンス漏れによるサイト破損を引き起こしやすい点に留意が必要です。

### `$to` ［リクエスト送信先ドメイン・ホストの指定］
* **構文例**： `/ads$to=evil.com|evil.org` / `/ads$to=evil.com|~not.evil.com`
* **概要**： リクエストの「送信先［宛先］ホスト名」を条件に指定して適用範囲を限定します（`$domain=` がリクエストの「発信元ページ」を指定するのに対する概念です）。
* **解説**： 共有CDN（Content Delivery Network：Webページ・画像・スクリプトなどの大容量コンテンツを、ユーザーの地理的な近くから高速・安定して配信するために世界中に分散配置されたサーバーネットワーク）や汎用APIエンドポイントから配信される広告・トラッキングスクリプトを、特定の悪質なホストへ向かう通信に限定して遮断し、正規利用されているサイト側では許可するといった精緻なコントロールが可能です。ただし、接続元（発信元）と接続先（宛先）の関係性を正確に把握して記述する必要があり、ルール設計の難易度が高くなります。

### `$third-party` ［サードパーティリクエストの制限］
* **構文例**： `||tracker.com^$third-party`
* **概要**： リクエスト送信先が、現在閲覧中のドメインと異なる場合のみ適用されます。
* **解説**： CDNやファーストパーティの必須スクリプトを保護しつつ、外部からのトラッキング通信のみを効率よく遮断できます。しかし、CNAMEクローキング（CNAME Cloaking：サードパーティのトラッキング用ドメインを、サイトのファーストパーティのサブドメイン名としてDNS上で別名設定し、アドブロッカーやブラウザの追跡防止機能をすり抜ける手法）等を用いてファーストパーティを偽装する最新のトラッカーに対しては効果を発揮しません。

### `$strict-first-party` / `$strict-third-party` ［厳格なファースト/サードパーティ判定］
* **構文例**： `||tracker.example.com^$strict-third-party`
* **概要**： `$strict-first-party`は参照元と送信先のホスト名が完全一致する場合（および参照元がない場合）だけをファーストパーティとして扱います。`$strict-third-party`は、通常の`$third-party`と異なり、親ドメインとサブドメイン間の通信もサードパーティとして扱います。運営主体（エンティティ）の同一性を判定する修飾子ではありません。
* **解説**： ホスト名単位で適用範囲を厳格化できる一方、サブドメイン間の正規通信を巻き込む可能性があります。AdGuard for Windows / Mac / Android / LinuxのCoreLibs v1.16以降で対応し、ブラウザ拡張機能では対応していません。

### 1.3 リソースタイプとマッチング条件
### `$all` ［すべてのリソースタイプへの適用］
* **構文例**： `||malware.example.com^$all`
* **概要**： ドキュメント、スクリプト、画像、ポップアップなど、通信の種類を問わずすべてのリクエストに対してブロックを強制適用します。
* **解説**： 修飾子なしのプレーンなルールでは通常対象外となるメインページ自体の読み込み `$document` や別窓展開 `$popup` を含む広い種類のリクエストを対象にします。AdGuard公式では `$all` は全コンテンツタイプ修飾子と `$popup` の組み合わせとして定義され、AdGuard for Chrome MV3では `$popup` の制約によりサポートされません。また、`$all` は `@@` を付けた例外ルールには使用できません。適用範囲が広いため、正規サイトやCDNを巻き込まないよう対象を十分に限定します。

### `$script`, `$image`, `$xmlhttprequest` 等 ［リソース指定］
* **構文例**： `||example.com/api^$xmlhttprequest`
* **概要**： 通信の種類を限定してルールを適用します。
* **解説**： ブロック対象を絞り込むことで、サイト必須リソースを巻き込むFalse Positiveの可能性を下げられます。反面、配信側が通信手法を変更（例: `script` から `fetch` への移行等）した際、ルールが一致しなくなる可能性があります。

### `$websocket` ［WebSocket接続の限定遮断］
* **構文例**： `||example.com/live-track^$websocket`
* **概要**： WebSocket（Web Real-Time Communicationとは異なる、ブラウザとWebサーバー間で一度確立したTCP接続を維持し、低遅延で双方向のデータ送受信を継続して行う通信プロトコル）による `ws://` および `wss://` 通信に対してのみルールを適用します。
* **解説**： WebSocketを使う特定の通信だけを対象にできます。チャット、通知、共同編集、ライブ配信など正規機能にも使われるため、送信先と再現手順を確認してから限定的に適用します。

### `$webrtc` ［削除済み］
* **構文例**： `example.com#%#//scriptlet('nowebrtc')`
* **概要**： ネットワーク修飾子 `$webrtc` は削除され、現在のAdGuard製品ではサポートされません。WebRTCを無効化する必要がある場合は、対応製品の信頼済みフィルタまたはユーザールールで `nowebrtc` スクリプトレットを使用します。
* **解説**： Web会議やP2P機能を破損させるため、対象ドメインを限定し、必要性を確認してから適用します。

### `$font`, `$media`, `$stylesheet` ［細分化されたリソースタイプ制御］
* **構文例**： `||fonts.example.net^$font` / `||video.example.com/ads/^$media`
* **概要**： Webフォント（`$font`）、動画・音声ストリームなどのHTML5メディア要素（`$media`）、スタイルシートCSS（`$stylesheet`）に限定してブロックを適用または例外解除します。
* **解説**： サードパーティ製Webフォントの読み込みを介したトラッキングの阻止や、モバイル回線での大容量な自動再生動画広告による通信量・バッテリー消費の浪費を確実に防止できます。一方で、 `$stylesheet` や `$font` を誤爆させると、サイトのアイコン（フォントアイコン）が消失したり、レイアウトが完全に崩壊するといった視覚的な問題が即座に発生します。

### `$method` ［HTTPリクエストメソッドの指定］
* **構文例**： `||example.com/api/track^$method=post|options` / `@@||example.com/api/login^$method=post`
* **概要**： GET、POST、OPTIONS、PUTなど、特定のHTTPリクエストメソッドに対してのみルールを適用または解除します。
* **解説**： 近年のトラッキング通信やアンチアドブロックはPOSTやOPTIONS（CORSプリフライトリクエスト：異なるドメイン間の通信において、実際のデータを送信する前に、サーバー側がその通信を許可しているかを確認するために自動送信されるOPTIONSメソッドの問い合わせリクエスト）を多用する傾向にあります。これらをピンポイントで遮断することで、通常のページロード（GETリクエスト）や正規APIを巻き込まずにトラッキングのみを無力化できる高い技術的精度を実現できます。反面、サイト仕様の変更によってメソッドが変更されると容易にすり抜けられる可能性があります。

### `$ping` ［トラッキング用ビーコン等の指定］
* **構文例**： `||example.com/track^$ping`
* **概要**： `navigator.sendBeacon()` や `<a ping>` 等によるPing/ビーコンリクエストに限定します。
* **解説**： ページ離脱時などにバックグラウンドで送信されるユーザーの行動トラッキング通信を確実に遮断できる機能ですが、サイト独自の計測APIなど、通常のXHR / Fetch通信で送られるトラッキングに対しては無効となります。

### `$popup` ［ポップアップの遮断］
* **構文例**： `||example.com^$popup`
* **概要**： 対象URLが新しいタブやウィンドウとして開かれる動作を検知してブロックします。
* **解説**： ユーザーの意図しない迷惑なリダイレクトやポップアップ広告を確実に防ぐことができる一方、正規の別窓リンク（ログイン画面や外部決済など）まで巻き込んで遮断してしまうFalse Positiveリスクが常に伴います。

### `$match-case` ［大文字・小文字の厳密な区別］
* **構文例**： `||example.com/AdBanner^$match-case`
* **概要**： URL文字列の大文字と小文字を厳密に区別して照合します。
* **解説**： 大 / 小文字が意味を持つ環境で正規リソースを巻き込まずに広告のみをピンポイントで遮断できます。ただし、配信側がURLを小文字に変更するだけで容易にすり抜けられるため、ルールの保守性が低下しやすい傾向があります。

### 1.4 通信の書き換えと動作変更
### `$empty` ［非推奨：空のレスポンスの返却］
* **構文例**： `||example.com/tracker.js$empty`
* **概要**： 接続エラーではなくダミーの「空のレスポンス」を返却します。ただし現在は非推奨で、AdGuard内部では `$redirect=nooptext` に変換されます。新規ルールでは `$redirect` を使用します。
* **解説**： スクリプトエラーを検知するアンチアドブロックを回避し、サイトの挙動崩れを防ぐことができます。その反面、通信自体は「200 OK」等として成功した扱いになるため、ブラウザ開発者ツールのネットワークパネルでのデバッグ時に直感的に把握しづらくなります。

### `$redirect` / `$redirect-rule` ［ローカルリソースへの置換］
* **構文例**： `||example.com/analytics.js$redirect=noopjs`
* **概要**： 外部スクリプトへのリクエストを遮断し、AdGuard内包のダミーリソースにすり替えます。
* **解説**： スクリプト読み込みが必須要件のサイトにおける「無限ロード」や「エラーによるレンダリング停止」を回避できます。一方で、MV3環境下など拡張機能がリダイレクトできるリソースに厳密な制限がある環境では、意図通りに動作しない場合があります。

### `$cookie` ［Cookieの制御・削除］
* **構文例**： `||example.com^$cookie=/.+/` ［対象ドメインの全Cookieを抑制］ / `@@||example.com^$cookie=/^session_/` ［特定Cookieの例外］
* **概要**： 通信自体は遮断せず、対象ドメインでやり取りされるHTTPヘッダーのCookieおよびSet-Cookieを抑制・削除します。
* **解説**： トラッキング用Cookieを対象にできますが、認証、設定、同意状態に使われるCookieを削除すると機能が壊れます。Cookie名、ドメイン、第三者性を限定し、サイトの利用条件を回避する目的では使用しません。

### `$header` / `$removeheader` ［HTTPヘッダーの操作と削除］
* **構文例**： `||example.com^$removeheader=referer` / `||example.com^$header=set-cookie:tracking`
* **概要**： `$removeheader`は一致した通信から指定ヘッダーを削除します。`$header`はレスポンスヘッダーの名前・値を条件に通信を照合する修飾子であり、任意のヘッダーを上書き・注入する機能ではありません。
* **解説**： たとえば `$header=set-cookie:tracking` は、該当するレスポンスヘッダーを持つ通信をルールの対象にします。ヘッダーを実際に削除する場合は `$removeheader`を使用します。認証、CORS、セキュリティポリシーを壊す可能性があるため、対象を狭く限定してください。

### `$urltransform` ［リクエストURLの動的書き換え］
* **構文例**： `||example.org^$urltransform=/(pref\/).*\/(suf)/$1$2/i`
* **概要**： 正規表現とキャプチャグループを用いて、リクエストURLを送信前に別のURLへ動的に変換・リダイレクトさせます。
* **解説**： トラッキング用の中継URLや追跡パラメータを改変できますが、正規表現の誤りで無関係なURLを破損させる危険があります。信頼済みフィルタ専用です。CoreLibs系製品に加え、AdGuard Browser ExtensionおよびAdGuard for Chrome MV3でもv5.5以降で対応していますが、MV3ではDNR由来の制限があるため、公式ドキュメントの制約を確認して使用してください。

### `$removeparam` ［トラッキングパラメータの高度な削除］
* **構文例**： `||example.com^$removeparam=/^utm_[a-z]+=/`
* **概要**： 正規表現を用いて特定のクエリパラメータを動的に削除します。
* **解説**： 通信自体は維持されるため、ページ遷移やリダイレクトを破壊せずにプライバシー保護を透過的に実行できる機能を持ちます。しかし、サイトのルーティングやセッション維持に必須のパラメータまで巻き込んで削除してしまうリスクがあります。

### `$replace` ［レスポンスボディの直接書き換え］
* **構文例**： `||example.com/api/$replace=/ad_enabled":true/ad_enabled":false/`
* **概要**： 正規表現を用いて、テキストベースのレスポンス中身を通信経路上で動的に置換します。
* **解説**： DOM操作より前のレスポンス本文を書き換えられる強力な機能です。AdGuard for Windows / Mac / Android等のCoreLibs製品とAdGuard for Firefoxで対応しますが、Chromium系ブラウザ拡張機能（AdGuard for Chrome MV3を含む）ではネットワークレベルでレスポンス本文を変更できないため利用できません。HTTPS通信の本文をCoreLibs製品で変更するには、その通信がHTTPSフィルタリングの対象になっている必要があります。

### `$csp` / `$permissions` ［セキュリティポリシーやブラウザ権限の強制制御］
* **構文例**： `||example.com^$csp=script-src 'self'` / `||example.com^$permissions=gyroscope=()`
* **概要**： HTTPレスポンスヘッダーにCSP（Content-Security-Policy / コンテンツセキュリティポリシー：クロスサイトスクリプティングやデータインジェクション等の攻撃を防ぐため、ブラウザが読み込み・実行を許可するリソースやドメインを厳格に制限するHTTPヘッダー）やPermissions-Policyを強制注入・変更します。
* **解説**： DOMに到達する前に悪意あるスクリプトを封じ込めたり、ジャイロセンサーや位置情報等のブラウザAPIへのアクセス権限を剥奪できます。ただし、サイト本来のCSPやポリシーと競合して正規スクリプトや機能が不全に陥るリスクが高く、一般ユーザーには原因特定が困難になりがちです。

### 1.5 デバッグ・ルールの優先度制御
### `$important` ［絶対的な優先適用］
* **構文例**： `||example.com/ads.js$important`
* **概要**： 例外ルールを含む、他のすべてのルールよりも優先してブロックを強制適用します。
* **解説**： 汎用例外ルールをすり抜けてくる悪質なトラッカーや広告を確実に遮断できる強力な手段となりますが、ルールの優先度階層を破壊するため、乱用すると意図しないブロックが発生した際のデバッグが極めて困難になります。

### `@@...$important` ［絶対的な例外・ホワイトリスト化］
* **構文例**： `@@||example.com/ads.js$important`
* **概要**： いかなる強力な遮断ルール（`$important` 付与を含むルール）の干渉も無効化し、最優先で通信を許可します。
* **解説**： サイト根幹を成す必須API等がサードパーティ汎用ルールによってFalse Positiveとなり遮断されている場合、確実に救済・復旧できます。しかし、ルールの権力が強すぎるため、指定が甘いと本来防ぐべき悪質トラッカーまで無条件に通過させてしまう重大なリスクを伴います。

### `$badfilter` ［既存ネットワークルールの無効化］
* **構文例**： `||example.com/ads.js$badfilter`
* **概要**： 購読しているフィルタに含まれる特定のネットワークルールを無効化します。
* **解説**： False Positiveの原因となっているサードパーティルールをピンポイントで解除でき、不具合のWorkaroundとして直結します。ただし、大元のルールが更新・削除された場合、このルール自体が不要なゴミとして残ってしまうため定期的な見直しが必要です。

### `$generichide` / `$genericblock` / `$specifichide` ［汎用および個別ルールの無効化］
* **構文例**： `@@||example.com^$generichide` ［汎用要素非表示の無効化］ / `@@||example.com^$specifichide` ［サイト固有の要素非表示のみを無効化］
* **概要**： 対象サイト上で、特定ドメインに縛られない汎用コスメティックルールや、逆にそのドメイン専用に書かれた固有のコスメティックルールを切り分けて無効化します。
* **解説**： サイト表示崩れが発生した際、「汎用ルールが原因か、そのサイト専用に書かれた個別ルールが原因か」を明確に切り分けるためのデバッグで極めて強力です。また、False Positiveを起こしている個別ルールを一時的に無効化しつつ基本的な広告除去機能（汎用ルール）を維持できるため、不具合対応のWorkaroundとしても最適です。

### `$stealth` ［ステルスモードの無効化］
* **構文例**： `@@||example.com^$stealth`
* **概要**： AdGuard独自のトラッキング保護機能による高度な介入（Cookieブロック等）を特定サイトで無効化します。
* **解説**： ログイン不可などの不具合が「通信ブロック」か「プライバシー保護機能の過剰介入」かを明確に見極めるデバッグに役立ちますが、対象サイトにおいてAdGuardの強力なプライバシー保護の恩恵が受けられなくなります。

## 2. コスメティックルール［DOM要素の非表示］

AdGuard for Androidでも軽く動作させるため、可能な限りシンプルな標準CSSセレクタ `##` を最優先します。

### 2.1 基本的な非表示・除外
### `##` ［基本のCSS非表示］
* **構文例**： `example.com##.ad-container`
* **概要**： ブラウザネイティブのレンダリングエンジンで直接処理される基本的な非表示記法です。
* **解説**： DOM操作の中で最も処理遅延とバッテリー消費が少ないため、モバイル環境において最優先で利用すべき記法ですが、クラス名やIDがランダム生成されるモダンな難読化広告要素の特定には無力です。

### `#@#` / `#@$#` / `#@?#` / `#@$?#` ［コスメティックルールの例外］
* **構文例**： `example.com#@#.banner` / `example.com#@?#div:has-text(広告)`
* **概要**：それぞれ通常の要素非表示、CSS注入、ExtendedCss要素非表示、ExtendedCssによるCSS注入の対応するルールを解除します。
* **解説**：購読フィルタによって正規コンテンツが消えるFalse Positiveを局所的に復旧するときに使います。例外側は、解除したい元ルールと構文・対象を正確に対応させ、サイト全体のコスメティックフィルタを一括解除する広い例外は避けます。

### `~` ［特定のドメインや要素の適用除外］
* **構文例**： `example.com,~shop.example.com##.ad-banner`
* **概要**： 非表示ルールの適用対象から特定のサブドメインやクラスを除外します。
* **解説**： 親ドメイン全体にルールを適用しつつ、表示崩れが起きる特定のサブドメインのみを容易にホワイトリスト化できますが、除外対象が長くなると可読性が下がり、ルール管理が複雑化します。

### 2.2 拡張セレクタによる高度な要素指定
### `#?#` ［拡張CSSルールの明示的適用］
* **構文例**： `example.com#?#.ad-box:contains(スポンサー)`
* **概要**： 標準CSSで指定できない要素を、AdGuard独自の拡張セレクタで指定します。
* **解説**： `:contains` 等を用いた複雑な要素指定ができ、構造が難読化された広告枠を特定できる強力な機能ですが、JavaScriptを介してDOMツリーを評価するため、多用するとページのレンダリング遅延やバッテリー消費を増大させます。

### `:is()` / `:where()` ［CSSセレクタのグルーピングと疑似クラス最適化］
* **構文例**： `example.com##:is(.ad, .banner):where([id*="sponsor"])`
* **概要**： 複数のセレクタを簡潔にまとめつつ、`:where()` は特異度（Specificity：CSSセレクタが特定の要素をどれだけ詳細・具体的に指示しているかを表す計算値で、複数のスタイルルールが競合した際にどの定義を最優先で適用するかを決定する基準）を0にリセットしてスタイル評価を行います。
* **解説**： `:is()` と `:where()` は標準CSSの疑似クラスで、複数のセレクタをまとめる用途に使えます。`:where()` は自身と引数の特異度を0として扱うため、スタイルの優先関係を管理しやすくなります。ただし、これだけで処理遅延やバッテリー消費が最小化されることを保証するものではありません。

### `:has` ［モダン疑似クラスの活用］
* **構文例**： `example.com##.article-card:has(> .sponsored-label)`
* **概要**： 特定の子要素を持つ親要素をターゲットにします。
* **解説**： AdGuardでは、`##` を使い、かつ内部に他の拡張CSSセレクタがない場合、対応環境ではネイティブの `:has()` を使用します。ネイティブ実装を利用できない製品・ブラウザではExtendedCssへフォールバックします。明示的に `#?#` / `#$?#` を使うとExtendedCss実装が使用されます。フォールバック時の性能影響はページ構造やセレクタに依存するため、実環境で確認します。

### `:contains` ［テキストフックによる要素指定］
* **構文例**： `example.com#?#.sponsor:contains(PR)`
* **概要**： 指定文字列を含む要素を非表示にします（uBlock Originの `:has-text` のAdGuard版）。
* **解説**： 構造が難読化された広告枠でも、視覚的なテキスト情報を手がかりに確実に消去できます。しかし、DOMツリー全体のテキストノードを走査するため、巨大なページではスクロール時のレンダリングジャンク（Rendering Junk：重いJavaScript処理や複雑なDOMツリー走査によってブラウザの処理負荷が高まり、画面の描画フレームレートが低下してスクロールやアニメーションがカクつく現象）の原因になり得ます。

### `:upward()` ［先祖要素への遡り］
* **構文例**： `example.com#?#.ad-text:upward(.ad-container)`
* **概要**： 引数に指定したCSSセレクタ、または数値分だけ階層を遡った先祖要素を探して非表示にします。
* **解説**： 広告テキスト等を起点にして、ランダムなIDを持つ親コンテナ全体をターゲットにする際に極めて有効な反面、過度な階層遡上はDOMの評価コストを上げ、False Positiveが発生した際の影響範囲が広くなります。

### `:xpath()` ［XPathを用いた要素指定］
* **構文例**： `example.com#?#:xpath(//div[@id="bar"]/p)`
* **概要**： XPath式を用いて対象要素を探索します。
* **解説**： 兄弟要素の配置関係など、CSSセレクタでは表現できない複雑な条件を持つ要素を指定できる最終手段として機能しますが、DOM評価の計算コストが非常に高いため、他の記法で代替できない場合のみに限定すべきです。

### `#$?#` ［拡張CSSによるスタイル指定］
* **構文例**： `example.com#$?#div[class^="Ad__"] { display: none !important; }`
* **概要**： 拡張CSSセレクタで一致した要素へ、波括弧内のCSSスタイルを適用します。`#$?#`だけで正規表現になるわけではありません。
* **解説**： 標準CSSで表現できる場合は `##` または `#$#` を優先し、拡張セレクタが必要な場合だけ使用します。

### `:matches-css()` / `:matches-css-before()` / `:matches-css-after()` ［計算済みスタイルや疑似要素に基づく非表示］
* **構文例**： `example.com#?#div:matches-css(position: fixed)` / `example.com#?#.banner:matches-css-before(content: *広告*)`
* **概要**： ブラウザが画面描画時に計算した実際のCSSプロパティ値や、`::before` および `::after` などの疑似要素に適用されたスタイル・テキスト内容を条件として要素を特定します。
* **解説**： クラス名やIDが完全に無意味なランダム文字列に生成され、かつテキストが疑似要素で描画される極めて高度な難読化広告や、画面を強制的に覆うアンチアドブロックオーバーレイを物理的な配置情報から正確に捕捉できる強力なセレクタです。しかし、ブラウザの計算済みスタイル（Computed Style）をリアルタイムで走査するため、DOM評価およびスタイル再計算のコストが全セレクタ中で最も高く、スマホ等では極端なレンダリングジャンクやバッテリー消費を招くため、他手法で解決できない場合のみの最終手段とすべきです。

### `:matches-attr()` ［属性値の正規表現マッチング］
* **構文例**： `example.com#?#div:matches-attr(data-ad-info=/^\[.*"sponsored".*\]$/)`
* **概要**： 特定のHTML属性値に対して正規表現を適用し、合致する要素を探索・特定します。
* **解説**： JSON文字列や複雑なパラメータが格納されたカスタムデータ属性（`data-*`）から、広告識別フラグのみを抽出してターゲティングできます。属性値内部を厳密に照合できるため高いブロック精度を誇りますが、DOMツリー内の全要素の属性文字列を解析するため、適切な親セレクタと組み合わせて走査範囲を限定しなければ、パフォーマンス遅延を発生させる要因になります。

### 2.3 要素に対するアクション［適用・削除］
### `:style(...)` ［CSSプロパティの安全な上書き］
* **構文例**： `example.com##body:style(overflow: auto !important;)`
* **概要**： 要素を隠すのではなく、指定したCSSプロパティを要素に直接適用します。
* **解説**： 強制注入 `#$#` より局所的に動作するため、スクロールロックの解除などを安全に行え、副作用を抑えられる特性があります。反面、特定の要素にしか影響を与えられないため、ページ全体に関わる複雑な動的スタイル変更には不向きです。

### `:remove()` ［DOMからの物理削除］
* **構文例**： `example.com##.floating-video:remove()`
* **概要**： `display: none` と異なり、DOMツリーから要素を完全に消去します。
* **解説**： 動画広告などのバックグラウンドでのメモリ消費とCPUリソースの浪費を根本から断ち切ることができますが、SPAでFalse Positiveを発生させると、ページをリロードしない限り復元できずサイト全体が機能不全に陥ります。

## 3. 高度なルール［スクリプトレット・HTML処理］

標準的なネットワークルールやコスメティックルールだけでは対応できない挙動に使う高度な手段です。AdGuardはクロスブロッカー互換性のためuBO・ABPのスクリプトレット構文もサポートしていますが、利用できるスクリプトレット名や引数、信頼済みルールの要件には差があります。AdGuard向けに作成する場合は、公式リファレンスで対応を確認し、AdGuardの `#%#//scriptlet(...)` 構文を使うと意図を明確にできます。

### 6.1 スクリプトレットの注入と例外
### `#%#//scriptlet` ［スクリプトレットによるJS関数ジャック］
* **構文例**： `example.com#%#//scriptlet('set-constant', 'adblockDetected', 'false')`
* **概要**： ページ読み込みの最初期にAdGuardの組み込みスクリプトを注入し、変数の固定化等を行います。
* **解説**： ネットワークブロック等では回避不可能な高度なJSベースのアンチアドブロックや強制ポップアップを完全に無力化できます。その反面、対象サイトの僅かなコード変更で即座にルールが陳腐化する欠点や、MV3環境での制限により将来的に機能しなくなるリスクがあります。

### `#%#//scriptlet('json-prune', ...)` / `json-prune` ［JSONデータの動的クレンジング］
* **構文例**： `example.com#%#//scriptlet('json-prune', 'ad_tags *.sponsor', 'ads_enabled')`
* **概要**： `JSON.parse()` と `Response.prototype.json()` の戻り値から、条件に合うプロパティを削除します。すべてのXHRレスポンスを直接処理する機能ではありません。対象APIは[公式ソース](https://github.com/AdguardTeam/Scriptlets/blob/master/src/scriptlets/json-prune.js)で確認できます。
* **解説**： 動画プラットフォームやモダンなSPA、アプリ内通信において、データ構造の中に組み込まれた広告情報だけを外科手術のように正確に除去できます。ただし、対象となるJSONスキーマ（JSON Schema：JSONフォーマットのデータ構造において、キーの名前、データの型、階層構造などの必須構文ルールや構造定義を記述した仕様書）が変わると機能しなくなるため、サイト側の更新頻度が高い場合は定期的なメンテナンスが必要です。

### `#%#//scriptlet('prevent-fetch', ...)` / `#%#//scriptlet('prevent-xhr', ...)` ［非同期通信のJSレイヤー遮断］
* **構文例**： `example.com#%#//scriptlet('prevent-fetch', 'log_event')` / `example.com#%#//scriptlet('prevent-xhr', 'analytics')`
* **概要**： 特定の文字列や正規表現に合致する `fetch` または `XHR` リクエストの発行をJSの実行レイヤーで直接ブロックします。
* **解説**： ネットワークルールでのブロックを検知して無限ループやエラーメッセージを発生させるアンチアドブロックに対して、APIそのものをスタブ（Stub：元の複雑な広告処理スクリプトやトラッキング関数の代わりに、エラーを発生させずに処理を即座に終了させる無害な空の関数や固定値を返す仮のコード）化することで、エラーを発生させずにトラッキングや広告通信のみを無効化できます。

### `#%#//scriptlet('prevent-addEventListener', ...)` ［イベントリスナーの登録阻止］
* **構文例**： `example.com#%#//scriptlet('prevent-addEventListener', 'click', 'ad_tracker')`
* **概要**： `addEventListener` を介した特定のイベント（`click`、`scroll`、`copy` 等）へのイベントリスナー登録を、指定文字列に合致する関数に限定して初期段階でブロックします。
* **解説**： ユーザーの画面クリックやスクロールをトリガーとして発動するトラッキングスクリプトや、右クリック・コピー禁止・デバッガ検知といったAnnoyances（Annoyances：広告とは異なるものの、ユーザーのWebブラウジング体験を妨げるCookie同意バナー、ニュースレター登録依頼、右クリックやコピー禁止等の迷惑機能の総称）をピンポイントで無力化できます。反面、サイトの正規のクリック操作やスクロール連動UIの処理関数を誤って巻き込んでブロックすると、リンク遷移や画面スクロール自体が不可能になる重篤なFalse Positiveを招くリスクがあります。

### `#%#//scriptlet('set-local-storage-item', ...)` / `#%#//scriptlet('set-cookie', ...)` ［ストレージとCookieの設定］
* **構文例**： `example.com#%#//scriptlet('set-local-storage-item', 'adblock_warning_shown', 'true')`
* **概要**： `set-local-storage-item` は `localStorage`、`set-cookie` はCookieに指定値を書き込みます。通常版で指定できる値には制限があり、後からサイトが上書きすることを阻止する機能ではありません。`sessionStorage` は別のスクリプトレットで扱います。[公式ストレージ実装](https://github.com/AdguardTeam/Scriptlets/blob/master/src/scriptlets/set-local-storage-item.js)・[公式Cookie実装](https://github.com/AdguardTeam/Scriptlets/blob/master/src/scriptlets/set-cookie.js)
* **解説**： CMP（Consent Management Platform：ユーザーに対して個人データ収集やCookie使用への同意を求めるプライバシーポップアップバナーを表示・管理するツールおよびプラットフォーム）による同意バナーの強制表示フラグや、アンチアドブロックの警告表示完了フラグを設定済みの状態に変更できる場合があります。ただし、同意・拒否の意味はサイト側のキーと値に依存し、バナー非表示だけではデータ収集の拒否を保証できません。通信やDOMを直接変更せずに済む反面、サイトがストレージのキー名を変更した際には即座に再調査とルール更新が必要になります。

### `#%#//scriptlet('abort-on-property-read', ...)` / `#%#//scriptlet('abort-on-property-write', ...)` ［プロパティアクセス時のスクリプト強制停止］
* **構文例**： `example.com#%#//scriptlet('abort-on-property-read', 'window.adblockDetector')`
* **概要**： サイトスクリプトが特定のJSプロパティを読み込もうと（または書き込もうと）した瞬間、そのアクセスを捕捉してスタックトレースからスクリプトの実行そのものを即座に中断させます。
* **解説**： 難読化され、かつ動的に変数名やクラス名を変える強力なアンチアドブロック検知スクリプトであっても、アクセス先となるブラウザやグローバルの特定プロパティをフックすることで、検知ロジックの発動を完全に阻止できます。一方で、強制的にスクリプトの実行例外を発生させて止める仕様上、同じJSファイル内にある正常な描画処理や通信関数まで同伴して停止してしまうケースが多く、サイト破損のデバッグと影響範囲の特定に高度な技術知識を要します。

### `#%#//scriptlet('remove-attr', ...)` / `#%#//scriptlet('remove-class', ...)` ［属性・クラスの動的削除］
* **構文例**： `example.com#%#//scriptlet('remove-attr', 'target', 'a[href*="ad.example"]')`
* **概要**： 指定したDOM要素から特定の属性やクラス名を動的に削除します。
* **解説**： クリック時に別窓を開かせる `target="_blank"` や、スクロールをロックする `class="modal-open"`、遅延読み込みで広告を発動させるカスタム属性などを安全に解除できます。CSSや `:remove()` では対応できない動的な挙動の修正に最適です。

### `#@%#` / `#@?#` ［拡張ルールのピンポイント例外］
* **構文例**： `example.com#@%#//scriptlet('set-constant', 'adblockDetected', 'false')`
* **概要**： 当該スクリプトレットの注入などを局所的に無効化し、動作を復旧させます。
* **解説**： 購読フィルタが原因でサイトの正規の処理が止まってしまった場合のWorkaroundとして効果的な解決策となりますが、どのスクリプトレットが原因で破損しているかを特定するためには、高度なデバッグスキルが要求されます。

### 6.2 HTML・CSSの強制操作
### `$$` ［HTMLフィルタリングルール］
* **構文例**： `example.com$$script[tag-content="ad-script-content"]`
* **概要**： ブラウザがDOMツリーを構築する前の生HTML応答データの段階で、対象要素を直接物理的に削除します。
* **解説**： DOM読み込みと同時に実行されてしまう悪質なインラインスクリプト等を、パースされる前に根本から消去できる極めて強力な機能です。一方で、指定できるセレクタが限定的であり、適用を誤るとページ構造自体を完全に破壊してしまいます。

### `#$#` ［CSSの強制注入］
* **構文例**： `example.com#$#body { overflow: visible !important; }`
* **概要**： 任意のCSSプロパティをページ全体に直接注入します。
* **解説**： コンテンツブロッカーを検知してスクロールをロックする悪質なオーバーレイの制限などを強制解除できますが、サイト自体の正規のレイアウト更新と競合し、予期せぬ表示崩れ（Z-indexの破綻など）を招くリスクが常に伴います。

## 4. プラットフォームの特性比較：MV3拡張機能 vs Android

カスタムルールを作成する前に、実行環境における技術的な制限と強みを正しく理解することが不可欠です。

| 機能・特性 | AdGuard ブラウザ拡張機能 MV3対応版 | AdGuard for Android (CoreLibs) |
| :--- | :--- | :--- |
| **主な動作レイヤー** | ブラウザ内部（DNR API依存） | OSレベル（通常はローカルVPN。HTTPSフィルタリング時はローカルプロキシで復号・検査） |
| **通信遮断の仕組み** | 事前宣言されたDNRルールによるブラウザエンジン処理 | ローカルプロキシでのリクエスト解析・遮断 |
| **ルールの件数上限** | **DNR制限あり**（拡張機能ごとに最低3万件の静的ルール枠が保証され、追加枠は全拡張機能で共有。実際の空きはAPIで確認） | **固定されたDNR上限はない**（ただし多すぎるとメモリ・バッテリーを消費） |
| **アプリ限定 (`$app`)** | **非対応**（ブラウザ内の通信のみ対象） | **対応**（対象アプリに適用範囲を限定） |
| **レスポンス置換 (`$replace`)** | **利用不可**（MV3の権限制限による） | **利用可能**（HTTPSフィルタリング有効時、経路上でテキスト直接改変） |
| **アドバンスド設定** | 基本的なユーザーインターフェースのみ | **ローレベル設定搭載**（パケット・ログ・VPN制御） |
| **設計時の主な制約** | DNRへの変換可否、ルール上限、更新方式 | HTTPSフィルタリングの対象、アプリ互換性、電池最適化 |

## 5. 学習手順：基礎からアドバンスド最適化へ導く6ステップ

### 【入門編：IT初心者向け】

### Step 1：アシスタントツールでの体験とプレーンな基本構文の習得

最初はゼロから手書きせず、AdGuard拡張機能の「要素をブロック」機能や、Androidアプリ内の設定を利用して、広告要素がどのようなルールに変換されるかを実体験します。

ここで扱う**「プレーンなホスト名指定（`||example.com^`）」**と**「標準的なCSSセレクタ（`##.ad-box`）」**は、AdGuardで広く使われる基本的なルール構造です。実際の処理コストや対応可否は製品・ルール内容・実行環境で異なるため、必要に応じて各製品で確認します [^1]。

### Step 2：通信遮断と要素隠蔽の使い分け（環境別の意識）

広告の「通信そのものを遮断するルール」と「画面に残った空白を隠すルール」の2種類の役割をマスターします。

通信をブロックすれば対象リソースの転送は抑えられますが、端末全体の電池消費が必ず減るとは限りません。MV3ではDNRへの変換可否とルール枠も考慮し、重複や不要に広いルールを避けます。

### Step 3：既存の汎用フィルタとの重複回避と例外指定

EasyListやAdGuard Base Filter等の購読フィルタと同じルールを、自分のユーザールールに二重に書かない習慣をつけます [^2]。

自分のカスタムルールは「特定のサイト・アプリでの漏れを補うルール」や「不具合を解除するための例外ルール（`@@`）」など、差分のみをシンプルに管理することが保守性を高める基本です [^4]。

---

### 【応用編：IT中級者向け】

### Step 4：公式・コミュニティリポジトリの査読とAdGuard構文への翻訳

世界中のメンテナーが改善を重ねるリポジトリ（AdGuardFilters, EasyList, uAssets等）のソースコードやIssueを読み解きます。

特にuBlock Origin公式（uAssets）で使われているアンチアドブロック突破の知見を参考にしつつ、そのままコピペするのではなく、AdGuardエンジンに適合した**スクリプトレット（`#%#//scriptlet`）構文**に正しく翻訳して適用するスキルを磨きます [^7]。

### Step 5：フィルタリングログを用いた切り分けと応急処置

ブラウザの開発者ツールと、AdGuard拡張機能・Androidアプリ内蔵の「フィルタリングログ」を使いこなすデバッグ技術を習得します [^5]。

正規サイトが表示崩れを起こした際（誤爆）、通信ブロックか、DOM非表示か、あるいはAdGuard独自のステルスモードの干渉かを切り分け、`$generichide` や例外ルールを用いて的確に応急処置（Workaround）を記述します [^3][^9]。

### Step 6：MV3のDNR制限とAndroidローレベル設定を確認する

拡張機能版（MV3）のDNRルール枠を効率よく使うため、重複ルールや不要な正規表現を減らします。要素隠蔽では、必要に応じてモダン疑似クラス（`:is()`, `:where()`）でセレクタをまとめますが、これはネットワーク用DNRルール数を増減させる仕組みではありません [^6][^8]。

Androidのローレベル設定は通常運用の最適化項目ではなく、特定の不具合調査や互換性調整に使います。理由がない限り既定値を維持します。

## 6. Android版「アドバンスド設定（ローレベル設定）」の解剖と最適化技法

AdGuard for Androidにおける「アドバンスド設定（詳細設定 / ローレベル設定）」は、OSのネットワークスタックやパケット解析エンジン（CoreLibs）に直接介入するための専門的なパラメータ群です。

**【アクセス手順】**

アプリの `「設定(⚙️)」` → `「一般設定」` → `（高度な設定モードをオン）` → `「詳細設定」` → `「ローレベル設定」` へと進みます。

### 6.1 カスタムルール作成とシステム最適化に役立つ主要設定項目

#### 1. ウォッチドッグ（Watchdog） / VPNの自動復元機能

* **機能概要**：Android OSの厳しい省電力機能によってAdGuardのバックグラウンドサービスが終了させられた際、自動的にローカルVPNプロセスを監視し再起動・復元する保護機能です。

* **活用とベストプラクティス**：Android端末のシステム設定側でAdGuardのバッテリー使用量を「制限なし（無制限）」に設定した上で本機能を有効化することで、意図しない広告ブロックの停止や、それに伴うカスタムルールの適用不全を防ぎます。

#### 2. DNS-over-HTTPS（DoH）フィルタリングの制御

* **機能概要**：端末上のアプリがシステムのDNSを迂回し、外部のDoH（暗号化DNS）サーバーへ向けて送信するリクエストをローカルプロキシでインターセプトし、AdGuardのフィルタリングルールを強制適用させる制御機能です。

* **利用上の注意**：アプリが独自に暗号化DNSを使う場合の扱いを調整できます。変更すると名前解決やアプリ互換性に影響し得るため、ログで対象通信を確認します。TLS証明書ピンニングはHTTPSフィルタリングの論点であり、DNS設定と混同しないでください。

#### 3. ECH（Encrypted ClientHello）ブロックおよびHTTP/3（QUIC）制御

* **機能概要**：最新の暗号化プロトコルであるECHやHTTP/3（QUIC）を介した通信を制御します。ECHが有効な場合、接続先ホスト名が暗号化されるため、通常のSNI監視によるドメインブロックが困難になる場合があります。

* **利用上の注意**：ECHやHTTP/3に関する設定名と既定値はバージョンで変わり得ます。変更は接続性や遅延に影響するため、一律に有効化せず、再現する不具合がある場合に限って比較検証します。

#### 4. IPv6フィルタリング

* **機能概要**：現行のAdGuard for Android v4.xには、IPv6ネットワークインターフェースが利用可能な場合にIPv6ネットワークをフィルタリングする「IPv6 filtering」設定があります。これはDNSのAAAA問い合わせへNXDOMAINや空応答を返す設定ではありません。

* **活用とベストプラクティス**：IPv6通信をAdGuardの保護対象に含めるかを制御する設定として扱います。DNSでブロックしたドメインへの応答方式は、別項目の「Blocking mode for adblock-style rules / hosts rules」でREFUSED・NXDOMAIN・Custom IP addressから選択します。IPv6通信の不具合を切り分ける場合も、DNS応答方式とIPv6フィルタリングを混同せず個別に確認します。

#### 5. ログ出力レベル（Logging Level）とトラフィックエクスポート

* **機能概要**：AdGuardアプリが記録するログの詳細度（デフォルト、デバッグ、トレース等）および「システムログとPCAPパケットキャプチャ」のエクスポートを制御します。

* **活用とベストプラクティス**：自作したスクリプトレット（`#%#//scriptlet`）や通信改変ルール（`$replace` 等）が対象アプリで機能しない場合、ログレベルを一時的に「デバッグ（Debug）」に引き上げてトラフィックを記録・解析することで、難読化された通信パターンを正確に特定できます。ただし、デバッグログはCPU負荷とストレージ書き込みを大幅に増大させるため、検証終了後は速やかに「デフォルト」に戻すことが鉄則です。

### 6.2 アドバンスド設定（ローレベル設定）調整のメリットとデメリット

* **メリット**：通常設定では切り分けにくいVPN、DNS、HTTPSフィルタリングの問題を診断できます。

* **デメリット**：システムネットワークの底層を変更するため、誤ったパケットタイムアウトやリダイレクトパラメータを指定すると、端末全体のインターネット接続が停止したり、著しいバッテリーの異常消耗、アプリの連続クラッシュを引き起こします。

**【公式メンテナーからの警告】**

AdGuard公式Knowledge Baseは、ローレベル設定の変更によってAdGuardの性能低下、インターネット接続の中断、セキュリティやプライバシーへの悪影響が生じる可能性があるため、経験があり技術的な意味を理解している場合、または公式サポートから指示された場合にのみ使用するよう注意しています。

## 7. ルール設計の鉄則：ベストプラクティスと環境別戦略

### 【初心者が守るべき3つの鉄則】

### 鉄則1：最初は「強力すぎる修飾子（`$all` や `$important`）」を封印する

* **背景・課題**：初心者ほど、広告を完全に消そうとして強制力を持つパラメータを多用しがちです。

* **ベストプラクティス**：ドメインの末尾に `$` を付ける際は、まずはタイプを指定しないシンプルな状態か、`$script`, `$image` 等の特定タイプのみに留めます。`$all` は複数のコンテンツタイプと `$popup` をまとめた修飾子で、AdGuard for Chrome MV3では `$popup` の制約によりサポートされません。CoreLibs等の対応製品で使う場合も、適用範囲が広いため正規通信を巻き込まないか確認します。

* **メリット**：強力な修飾子を避けることで、サイトの認証システムやログイン機能を巻き込んでページやアプリを破壊するリスクを大幅に減らせます。

* **デメリット**：強制力が弱い分、悪質なトラッカーや巧妙な広告がすり抜ける可能性がありますが、それは個別リソースの指定で厳密に補うのが正統派です。

### 鉄則2：「通信ブロック」を主役とし、「要素隠蔽」を脇役にする

* **背景・課題**：広告を画面で見えなくすること（要素隠蔽）ばかりに頼ると、バックグラウンドで広告データのダウンロードやトラッキング通信が走り続け、端末のリソースを無駄に消費します。

* **ベストプラクティス**：広告専用であることと正常な通信への影響を確認できたドメインには、 `||ad-server.com^` のように通信そのものを根元から遮断するルールを記述します。コスメティックルール（`##.ad-banner`）は、通信を止められないファーストパーティ配信の広告枠や、空白の枠線を消すためだけに補助的に使用します。

* **メリット**：広告用リソースの通信自体を遮断できれば、そのリソースのデータ転送や後続処理を減らせる場合があります。ただし、端末全体のバッテリー消費がどの程度変化するかはサイト、アプリ、通信方式、端末環境に依存します。

* **デメリット**：配信元ホスト名が頻繁に変わるスクリプト生成型の広告には追従できず、都度ホストのログ確認が必要になります。

### 鉄則3：自作フィルタは最小限に保ち、複雑な不具合は公式チームへ報告する

* **背景・課題**：個人で数千行に及ぶ巨大なカスタムルールを維持・管理することは困難です。

* **ベストプラクティス**：自作のユーザールールは数十〜数百行程度の「自身の利用環境向け調整用」に留めましょう。また、AdGuardエンジンはマッチング高速化のためにURLを4096文字で切り詰める仕様があるため、長すぎるURLをそのままルール化しないよう注意が必要です。汎用フィルタですり抜ける広告を見つけた場合は、GitHubのオープンなIssues等を通じてAdGuard公式メンテナーに報告し、大元のリスト（AdGuardFilters）を修正してもらうのが最も効率的です。

* **メリット**：日々のルール更新や仕様変更への追従という重いメンテナンス負荷を公式チームやコミュニティに分散でき、常に最適な状態を保てます。

* **デメリット**：報告から公式リストに修正が反映され、自身のアプリや拡張機能に配信されるまで数日間〜数週間のタイムラグが生じます。

---

### 【中級者が極めるべき4つの鉄則】

### 鉄則4：ネットワークルールは「適用先（`$domain=`）」と「アプリ（`$app=`）」で隔離する

* **背景・課題**：広範な通信ブロックは、共有CDNを利用する正規サイトや、OS内の他アプリの正常通信までまとめて破壊します。

* **ベストプラクティス**：特定のウェブサイトでのみ悪用されているスクリプトには、`||example.com/ads.js$domain=test.com` と発信元を厳密に指定します。AdGuard for Androidでは、対象アプリだけに適用したいルールには `||ads.example.net^$app=com.example.targetapp` とアプリ識別子を指定し、他アプリへの適用を制限します。共有ドメインや必要なAPIを遮断しないか、ログと実際の動作で確認します。

* **メリット**：ピンポイントに条件を付けることで、他サイトや他アプリへの影響範囲を狭めつつ、対象の広告・トラッキング通信だけにルールを適用しやすくなります。

* **デメリット**：サイトやアプリ側がサブドメインや配信ルートを変更した際、ルールのメンテナンス漏れにより突然広告が復活するケースがあります。

### 鉄則5：コスメティックルールは疑似クラスを活用し、「スタイル再計算コスト」を極小化する

* **背景・課題**：HTML要素を消去するルールは、ブラウザの描画エンジンが画面を描画するたびに計算されます。

* **ベストプラクティス**：標準CSSセレクタ `##` で記述できる要素を最優先します。複雑な条件を組む際は `:is(.ad, .sponsor):where([id*="banner"])` のように、`:where()`で特異度（Specificity）をゼロにして上書きしやすさを管理できます [^6]。ただし、特異度が低いこと自体は処理速度の保証ではなく、性能はセレクタの探索範囲や条件にも左右されます。また、uBlock Originの記法をそのまま使うのではなく、AdGuardのエンジンが解釈できる形に落とし込むことが重要です。

* **メリット**：`:is()` で条件をまとめたり、`:where()` で特異度を0にしたりすることで、セレクタの意図や優先関係を管理しやすくなります。これ自体が処理速度の向上やレンダリングジャンク防止を保証するものではありません。

* **デメリット**：`:matches-css()` や `:matches-attr()`、正規表現セレクタ `#$?#` などの重い独自拡張セレクタは、DOM全体の評価と計算をリアルタイムで行うため、バッテリー消費と遅延が跳ね上がります。これらは他手法で代替できない場合の「最終手段」とすべきです。

### 鉄則6：スクリプトレット注入はAdGuard専用記法（`#%#//scriptlet`）を使用する

* **背景・課題**：JavaScript実行レイヤーへの介入は、アンチアドブロックを無力化する極めて強力なアプローチです。

* **ベストプラクティス**：uBlock Origin特有の `##+js(...)` をそのまま書くのではなく、AdGuardエンジンの実行効率と互換性に最適化された `#%#//scriptlet(...)` 構文に統一します。検知スクリプトに対しては `abort-on-property-read`、動画広告などのインラインデータには `json-prune` を局所的に適用します [^7]。なお、MV3拡張機能ではブラウザのセキュリティ仕様により一部スクリプトレットが制限されるため、不都合があればAdGuard for Android側（OSレベルブロック）での対策を検討します。

* **メリット**：通常の通信・DOMブロックでは突破不可能な最新のアンチアドブロック機能や、JSONデータに不可分で組み込まれた広告を、エラーを発生させずに正確に削ぎ落とせます。

* **デメリット**：サイト側のJSコードの変数名やJSONスキーマが少しでも変更されると即座に機能しなくなります。また、強力なスクリプト割り込みにより正常な描画処理まで停止させ、ページがフリーズする重大なリスクを持ちます。

### 鉄則7：誤爆（False Positive）対応は「根本原因の無効化」から行う

* **背景・課題**：購読フィルタの影響で正規サイトやAndroidアプリの動作が崩れた際、無関係なルールを闇雲に付け足して解消しようとしてはいけません。

* **ベストプラクティス**：AdGuardの「フィルタリングログ」で問題のURLを特定し、その通信をブロックしている特定のルールに対して例外 `@@||example.com^$script` を記述するか、当該ルールのみを無効化する `$badfilter` を適用します [^5]。コスメティックの誤爆であれば、`$generichide` や `$specifichide` を対象ドメインに設定し、汎用ルールと個別ルールのどちらが不具合を起こしているかを論理的に切り分けます [^3]。

* **メリット**：既存の購読フィルタ（サードパーティ製リスト）を直接いじらず、自分専用のユーザールールだけで不具合を安全かつ綺麗に解消（Workaround）できます [^4]。

* **デメリット**：後に大元のリスト側で公式修正がなされた場合、自分で書いた `$badfilter` や例外ルールが「不要なレガシールール（ゴミ）」として残留するため、定期的な見直しと整理が必要です。

## 8. AdGuard Filters issuesで必要となる実践知識

ここではフィルタ作者向けの全手順ではなく、問題を再現し、原因を切り分け、保守担当者が検証可能な報告を作るための要点を扱います。公式Issueテンプレートは、直接GitHubへ投稿するより先に[AdGuard Web Reporting Tool](https://adguard.com/kb/guides/report-website/)を使うことを推奨しています。

### 8.1 問題の分類

| 分類 | 意味 | 代表例 |
| :--- | :--- | :--- |
| **False Positive** | 正常なコンテンツや機能をフィルタが誤って阻害する問題 | ログイン不能、ボタン・動画・コメント欄が動かない、正規画像が消える、無限ロード |
| **Missed Ad / Ad Leftover** | 広告が残る、または広告本体の遮断後に枠・余白が残る問題 | バナー、動画広告、空の広告枠 |
| **Annoyance** | 広告以外の閲覧妨害要素 | Cookie通知、ニュースレター、アプリ・SNS誘導、ポップアップ、固定バナー |
| **Anti-Adblock** | コンテンツブロッカーの利用を検出して閲覧を妨げる仕組み | 警告、オーバーレイ、コンテンツ非表示、動画停止 |
| **Missed Tracker** | 分析・追跡通信が遮断されずに残る問題 | ビーコン、分析API、追跡パラメータ |

分類は提案するルールの収録先にも関係します。例えば、広告ではないCookie通知を「広告」として報告せず、Annoyanceとして区別すると確認が進みやすくなります。

### 8.2 報告前の切り分け

1. AdGuard、ブラウザ、フィルタを最新版へ更新し、ページを再読み込みして再現を確認します。
2. サイトやアプリが壊れる場合は、AdGuardの保護を一時停止したときに問題が解消するか確認します。解消しなければ、AdGuardフィルタ以外が原因の可能性があります。
3. 問題が起きる最小限の手順とURLを記録します。ログインなど特別な条件があれば明記します。
4. フィルタリングログで問題発生時刻付近のBlocked、Allowed、Modified、Redirected、Whitelisted等の処理結果と、一致したルールを確認します。
5. 原因候補のルールまたはフィルタだけを一時的に無効化し、再現結果が変わるか確認します。恒久的に無効化する前に元の状態を記録します。
6. 他の広告ブロッカー、DNSフィルタ、Private DNS、VPN、hosts、Pi-hole、NextDNS、personalDNSfilter等を併用している場合は、可能な範囲で一時的に切り分けます。
7. 必要に応じてプライベートブラウジング、新しいプロファイル、キャッシュを無視した再読み込みで確認します。ただし、Cookie削除はログアウト等を招くため、必要性を確認してから行います。
8. 結果を「AdGuard有効時」「無効時」「原因候補だけ無効時」に分けて報告します。

切り分け中にセッションCookie、認証URL、個人名、メールアドレス等を取得した場合は、スクリーンショットやログを公開する前に必ず伏せます。

### 8.3 Filtering Logの読み方

フィルタリングログでは、リクエストURL、発信元、リソースタイプ、処理結果、および一致したルールを組み合わせて確認します。表示名は製品・バージョンで異なる場合がありますが、概ね次の意味です。

| 結果 | 読み方 |
| :--- | :--- |
| **Blocked** | ネットワークルールによって通信が遮断された |
| **Allowed** | ブロック対象ではなく許可された |
| **Modified** | ヘッダー、Cookie、URL、応答等にルールによる変更が加わった |
| **Redirected** | `$redirect`等によって別のローカルリソース等へ置換された |
| **Whitelisted** | 例外ルールによって許可された |

False Positiveでは「壊れた機能が要求したURL」と「そのURLに一致したルール」を対で記録します。単に大量のログを貼るより、例えば「`https://example.com/api/comments` が `||example.com/api^$xmlhttprequest` によりBlockedとなり、当該ルールを無効化するとコメントが表示される」と示す方が再現性の高い報告になります。コスメティックルールやスクリプトレットによる問題はネットワーク通信として現れないことがあるため、ログにBlockedがないことだけでAdGuardが無関係とは断定できません。

### 8.4 Browser ExtensionでのDevTools確認

* **Elements**：残っている広告や消えた正規要素のHTML、class、id、属性、親子関係を確認します。動的に変化する文字列や、別用途でも使われる汎用classだけを根拠にしません。
* **Network**：広告・追跡・API通信のURL、リソースタイプ、発信元、ステータス、再現時刻を確認します。認証情報を含むRequest HeadersやPayloadを公開しないでください。
* **Console**：操作不能や無限ロードに関連するJavaScriptエラーを確認します。ページ側に元から存在する無関係なエラーもあるため、AdGuardの有効・無効で差を比較します。

DevToolsはフィルタリングログを置き換えるものではありません。両方の情報が一致するかを確認します。

### 8.5 Element Picker / Assistantの扱い

要素選択機能が生成したルールは出発点として有用ですが、そのまま報告・採用する前にセレクタを確認します。ランダムなclass、頻繁に変わる数値、過度に長いDOM階層、汎用的すぎる属性を含むルールは壊れやすい傾向があります。

```adblock
example.com##.ad-banner
```

このように対象ドメインを限定し、意味が安定しているclassや属性を使う単純な標準CSSセレクタを優先します。標準CSSで解決できない場合に限ってExtendedCssを検討します。

### 8.6 False Positiveを抑えるルール設計

* グローバルな `##.ad` より `example.com##.ad` のように、必要なサイトへ適用範囲を絞ります。
* ネットワークルールは可能なら `$script`、`$image`、`$xmlhttprequest` 等でリソースタイプを限定します。
* 正規表現、`:xpath()`、`:matches-css()`、Scriptlet、HTMLフィルタリングは、より単純なルールで解決できない場合に使います。
* 動的classや現在のDOM階層数だけに依存するセレクタを避けます。
* `$document` の例外やフィルタリング全体を解除する回避策は影響が大きいため、より狭い通信・コスメティック・Scriptlet例外を先に検討します。
* 提案ルールは広告を消すことだけでなく、ログイン、動画、コメント、決済、スクロール、戻る操作等の正規機能も確認します。

### 8.7 公式Issueテンプレートに沿った報告項目

[AdguardFiltersのBug reportテンプレート](https://github.com/AdguardTeam/AdguardFilters/blob/master/.github/ISSUE_TEMPLATE/bug_report.yml)で必須または選択を求められる主な項目は次のとおりです。

* AdGuard、ブラウザ、フィルタを更新済みであること
* サイト・アプリ破損では、AdGuardを無効化すると解消すること
* 使用製品とAdGuardのバージョン
* 問題の分類、ブラウザ、Desktop / Mobile
* 問題のURLまたは影響を受けるアプリへのリンク
* 有効なAd Blockingフィルタ、および該当するPrivacy、Annoyances、Language-specific、DNS等のフィルタ
* 有効なTracking protection（旧Stealth Mode）設定
* 問題の説明とスクリーンショット
* 報告に個人情報が含まれていないことの確認

公式フォームに加えて、再現手順、実際の結果、期待する結果、User rules・カスタムフィルタ、他のブロッカー・DNS・VPNの併用状況、原因候補のルール、関係するログを添えると調査に役立ちます。パスワード、Cookie、トークン、決済情報等は添付しません。

### 8.8 MV3とAdGuard for Androidの主な違い

AdGuard公式構文リファレンスの互換性表に基づく代表例です。バージョン更新で対応状況が変わるため、最終判断は各修飾子の公式表を確認してください。

| 構文・機能 | Browser Extension MV3 | AdGuard for Android（CoreLibs） | 主な用途・注意 |
| :--- | :---: | :---: | :--- |
| `$app` | 非対応 | 対応 | Androidではパッケージ名でアプリを限定 |
| `$domain` / `$denyallow` / `$to` | 対応（構文ごとの制限を確認） | 対応 | 発信元・除外・送信先を限定 |
| `$method` / `$header` | 対応（制限付きの場合あり） | 対応 | HTTPメソッド・レスポンスヘッダー条件 |
| `$strict-first-party` / `$strict-third-party` | 非対応 | 対応 | ホスト名一致を厳格に判定 |
| `$cookie` | 制限付き対応 | 対応 | MV3ではCookieを削除できない場合がある |
| `$removeheader` | 制限付き対応 | 対応 | MV3では否定・例外ルール等に制限がある |
| `$replace` | 非対応 | 対応（trustedのみ） | Chromium拡張はネットワーク応答本文を書き換えられない |
| `$redirect` | 例外等に制限あり | 対応 | 無害なローカルリソースへ置換 |
| `$redirect-rule` | 非対応 | 対応 | MV3ではDNRルールへ変換されない |
| `$removeparam` | 制限付き対応 | 対応 | MV3では正規表現・否定・例外ルール等が非対応 |
| `$urltransform` | v5.5以降で制限付き対応 | 対応（trustedのみ） | MV3では正規表現や置換等にDNR由来の制限がある |
| HTMLフィルタリング `$$` | 非対応 | 対応 | DOM構築前の応答本文から要素を除去 |
| コスメティックルール / Scriptlet | 対応するが実行方式・対応構文に製品差 | 対応 | ネットワークDNRとは別経路で実行される機能を含む |

MV3はネットワークルールをDNRへ変換して適用するため、CoreLibsと同じAdGuard構文が記載されていても、同一の挙動・制限とは限りません。一方、コスメティックフィルタやScriptletまで一律に「MV3では使えない」とみなすのも不正確です。製品、バージョン、構文ごとに確認します。

### 8.9 AdGuard構文とuBO互換構文

AdGuardは一部のuBO・ABP互換構文を解釈できますが、構文を受理することと、スクリプトレット名・引数・権限・実行タイミングまで完全互換であることは同義ではありません。

| 目的 | AdGuardで意図が明確な記法 | 見かける互換記法 | 注意 |
| :--- | :--- | :--- | :--- |
| Scriptlet | `example.com#%#//scriptlet('name', 'arg')` | `example.com##+js(name, arg)` | 対応する名前・別名・引数をAdGuard Scriptletsで確認 |
| ExtendedCssの文字列条件 | `example.com#?#div:contains(広告)` | `example.com##div:has-text(広告)` | 製品・版による互換性を確認し、AdGuard向けでは公式記法を優先 |
| Scriptlet例外 | `example.com#@%#//scriptlet(...)` | 対応するuBO例外構文 | 元の注入ルールと正確に対応させる |

trusted Scriptletなど信頼済みフィルタ限定の機能があります。AdGuardでは公式フィルタ、trustedとして追加したカスタムフィルタ、User rulesが信頼済みとして扱われますが、公開フィルタへの提案では権限要件と安全性を別途確認します。

## 9. 専門用語解説と脚注（Reference Glossary）

本レポートで使用されている専門用語の解説と、参照すべき公式・信頼性の高い正確なリファレンスURLです。

[^1]: **アシスタントツール / 要素選択ツール**

  画面上で消したい広告をマウスやタップで選択し、対応するブロックルールを自動生成するツール。AdGuard ブラウザ拡張機能やuBlock Originに搭載されており、初学者の学習に最適です。

  * **参照**：[uBlock Origin Wiki - Element picker](https://github.com/gorhill/ublock/wiki/Element-picker) / [AdGuard ナレッジベース - 独自の広告フィルタを作成する方法](https://adguard.com/kb/ja/general/ad-filtering/create-own-filters/)

[^2]: **汎用フィルタ（EasyList / AdGuard Base Filter）**

  世界中の一般的な広告やトラッカーを遮断するため、コミュニティやAdGuard公式チームによって日夜メンテナンスされている基準となるルールリスト。

  * **参照**：[EasyList Official](https://easylist.to/) / [AdGuard Filters Repository](https://github.com/AdguardTeam/AdguardFilters)

[^3]: **誤爆（False Positive）**

  本来広告ではない正規のウェブコンテンツやアプリの必須機能（ログイン、動画再生、決済画面等）が、ブロックルールに誤って合致して機能不全に陥る現象。

  * **参照**：[AdGuard ナレッジベース - AdGuardフィルタ一覧と不具合・誤爆報告について](https://adguard.com/kb/general/ad-filtering/adguard-filters/)

[^4]: **応急処置（Workaround）**

  フィルタの誤爆やサイト・アプリの破損が発生した際、公式リストで根本修正されるまでの間、ユーザーが独自にユーザールールへ追加する一時的な回避策や例外ルールのこと。

[^5]: **フィルタリングログ（Filtering Log）**

  AdGuardのブラウザ拡張機能やAndroidアプリに内蔵されている監視機能。通信の遮断・許可や関連ルールを確認してデバッグできます。ただしAdGuard for Chrome MV3では、DNR APIの制約により実際に適用されたルールを常に取得できるわけではなく、Filtering logに「適用されたと推定されるルール（assumed rule）」が表示される場合があります。

  * **参照**：[AdGuard Blog - In-Depth Features Overview: AdGuard for Android](https://adguard.com/en/blog/in-depth-review-adguard-for-android.html)

[^6]: **特異度（Specificity）**

  CSSセレクタが「どれだけ詳細に特定の要素を指定しているか」を表す計算値。`:where()` 疑似クラスでは、その疑似クラスと引数のセレクタが特異度計算に寄与しないため、スタイルの優先関係を管理しやすくできます。これは処理速度の最適化を保証する仕組みではありません。

  * **参照**：[uBlock Origin Wiki - Static filter syntax](https://github.com/gorhill/ublock/wiki/static-filter-syntax)

[^7]: **スクリプトレット（Scriptlet）**

  ページ読み込みの初期段階にAdGuardエンジンが注入する小さなJSプログラム。アンチアドブロックの検知関数をフックして無力化したり、インラインデータの広告を取り除きます。

  * **参照**：[AdGuard ナレッジベース - 独自の広告フィルタを作成する方法](https://adguard.com/kb/ja/general/ad-filtering/create-own-filters/)

[^8]: **MV3（Manifest V3）とDNR（Declarative Net Request）**

  ブラウザ拡張機能の仕様（MV3）で使用される通信制御APIです。拡張機能ごとに最低3万件の静的ルール枠が保証され、それを超える枠はインストール済み拡張機能間で共有されます。利用可能数は `getAvailableStaticRuleCount()` で実行時に確認できるため、「常に最大30万件」とは限りません。

  * **参照**：[AdGuard ナレッジベース - 独自の広告フィルタを作成する方法（DNR互換性解説）](https://adguard.com/kb/ja/general/ad-filtering/create-own-filters/)
  * **参照**：[Chrome Extensions - declarativeNetRequest API](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest)

[^9]: **DOM（Document Object Model）**

  ウェブページを構成するHTMLやXMLの要素をツリー状の構造として表現した仕組み。コスメティックルールはこのDOMツリーを走査・評価して広告要素を見つけ出し非表示にします。

  AdGuard特有の文法や推奨作法を体系的に習得できます。uBlock Originとの構文の違い `##+js(...)` ではなく `#%#//scriptlet(...)`、`:has-text(...)` ではなく `:contains(...)` を用いる点や、拡張CSSルール `#?#` 等の理解に役立ちます。一方、最新のアンチアドブロック突破などの実践的ロジックは網羅されていないため、uAssets等との併用が必要となります。

* **[AdguardTeam/AdguardFilters](https://github.com/AdguardTeam/AdguardFilters)**

  AdGuard公式の最新ルールリポジトリであり、モバイルアプリ向けの指定 `$app` や独自スクリプトレットなど、AdGuard環境に特化した実践的なルールの記述法を直接参照できる最大の強みがあります。ただし、ルール群は用途別（Base, Mobile, Annoyances等）にモジュール構造（Module Structure：大規模なフィルタ群やプログラムを、単一の巨大なファイルとして管理するのではなく、用途、プラットフォーム、機能ごとに独立した複数のファイルやディレクトリに分割・整理する設計手法）として細かくディレクトリ分割されているため、目的の記述を探し出すにはリポジトリの設計方針に対する深い理解が求められます。

* **[AdGuard Filters Issue Template](https://github.com/AdguardTeam/AdguardFilters/blob/master/.github/ISSUE_TEMPLATE/bug_report.yml)**

  問題報告前の更新確認、製品・バージョン・問題分類・ブラウザ・端末種別・URL・有効なフィルタ・Tracking protection設定・説明・スクリーンショット・プライバシー確認など、報告時に必要な項目を定義する公式テンプレートです。

* **[AdguardTeam/Scriptlets](https://github.com/AdguardTeam/Scriptlets)** / **[AdguardTeam/ExtendedCss](https://github.com/AdguardTeam/ExtendedCss)** / **[AdguardTeam/CoreLibs](https://github.com/AdguardTeam/CoreLibs)**

  Scriptletの正式名称・別名・引数、非標準セレクタの実装、Android等で使われるフィルタリングエンジンの更新内容を確認するための公式ソースです。

* **[AdGuard Blog](https://adguard.com/en/blog/index.html)**

  広告ブロックの最新トレンドやMV3対応ロードマップ等を発信する公式ブログです。業界全体の動向や大型アップデートを追うのに有用ですが、一般向けのキャンペーン記事も多く混在しています。なお、疑似クラス `:has(...)` 等のネイティブ実装状況や、処理負荷を低減するフィルタ記述のベストプラクティスといった専門情報はここには掲載されないため、高度な開発情報は公式ドキュメントやGitHub（CoreLibs等）を別途参照する必要があります。

* **[easylist / easylist](https://github.com/easylist/easylist)**

  すべての原点である汎用ネットワークルールの集積であり、長年のコミュニティの運用によって高度に洗練された、最も堅牢で安定したルールの記述法を学べるリポジトリです。MV3環境や最新の難読化広告にはこれ単体では対応しきれない側面もあります。また、独自の検証環境でテストしたルール群やスクリプトをコミュニティ内で迅速に共有する際には、GitHub Gist（Gist：GitHubが提供する、単一または複数のコードスニペットや設定ファイル、カスタムルールリストなどを簡単に公開・管理・共有できる簡易リポジトリサービス）が活用されることも多くあります。

* **[uBlockOrigin/uAssets](https://github.com/uBlockOrigin/uAssets)**

  uBlockOrigin/uAssetsには高度な動的要素指定やアンチアドブロック突破のロジック群がまとめられており、現代最高峰のフィルタリング技術の参考として有用です。AdGuard環境へ適用する場合、現在では `##+js(...)` 構文がそのまま解釈されることが多いですが、uBlock Origin固有の特権スクリプトレット（trusted系など）の存在や引数の仕様差異があるため、AdGuard側のエンジンとの互換性確認や代替ロジックへの調整が必要となります。
